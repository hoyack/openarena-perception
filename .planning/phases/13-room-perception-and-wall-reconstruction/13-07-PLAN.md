<hook_site_decision>

**fit_rooms() hook site (LOCKED):** `item_tour.py` tick loop, immediately after `self.learned_map.update(...)` on line 639, inside the same `if self.agent.nav.pos and gs.frame is not None:` block. Unconditional per-tick call; cadence gate lives inside `LineFitter.fit()`.

Rationale: `fit_rooms()` already short-circuits when the raycast cloud is below 20 samples and `LineFitter.fit()` is internally cadence-gated. The observable per-tick cost on a "not yet" tick is microseconds. Putting it inside the existing pos+frame gate means we only fit when the bot has a known position and a frame — matching the conditions under which `update()` just appended a new raycast, so it's the first tick where fitting a newly-enlarged cloud could possibly produce different output.

**note_item() hook site (LOCKED):** `item_tour.py` tick loop, in the SAME block, immediately after the new `fit_rooms()` call. On each tick we iterate `self._route` and call `self.learned_map.note_item(name, x, y)` for every (name, x, y, z) entry.

Rationale for this hook (NOT the ReactiveAgent on_item_seen callback):
1. `self._route` is a stable, known-in-advance list of tour waypoints — each entry is `(name, x, y, z)` from the AAS item entity list. We already have `(name, x, y)` in scope — no new perception work needed.
2. Rooms don't exist at tour-start time (raycast cloud is still empty), so a startup-only `note_item()` pass would route zero items. Calling it per-tick is self-correcting: as `fit_rooms()` produces new rooms 10-15 s in, the next `note_item()` pass routes the tour items into them.
3. `note_item()` has internal name-dedup AND early-returns when `rooms` is empty. Per-tick invocation on a ~20-item route costs approximately: (empty-rooms early return until fit_rooms produces rooms) + (once rooms exist: N_items × N_rooms × cv2.pointPolygonTest, approximately microseconds total for ~20 items × ~5 rooms). Well inside the per-tick budget.
4. Avoids the hazard the task description warned about — "per-tick note_item while item is in view would spam the list". We're not using a "while visible" signal at all; we're using the known-in-advance tour route, which is stable and guaranteed correct.

Alternative considered and rejected: hooking into ReactiveAgent item-observed callbacks. The agent's item list (`self.agent.items`) is populated at init from the AAS file, not from per-tick vision, and there is no `on_item_seen` style callback to subscribe to. The tour route IS the observation stream. Hooking here is simpler and more reliable.

</hook_site_decision>
