# Phase 12.1: Code Review Report

**Reviewed:** 2026-04-11
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Phase 12.1 polish changes (square 360x360 wireframe + square 360x360 minimap stacked in a 760x720 window, AAS `areas_on_floor` current-floor filter, minimap AAS overhead rework) are well-structured and covered by tests. The new `areas_on_floor` helper is clean, correctly skips the dummy area 0, and has thorough unit coverage. Panel layout constants are derived (no hardcoded HUD_WIDTH) and backward-compat aliases are preserved.

Two new issues were introduced by the polish changes:

1. The 20px status bar is drawn on top of the subsurfaces at the bottom of the window, clobbering approximately the last 12 pixels of actual minimap content and the bottom of the stats panel.
2. `MinimapPanel._draw_aas_overhead` swallows all exceptions silently, which can hide real bugs in the AAS overhead path.

Three info-level observations cover hardcoded palette values, a minor `_draw_separators` ordering cosmetic, and grid line bounds.

Pre-existing Phase 12 warnings (HUDState.load bare `except`, hud_schema, navigator sleep, advisor fence strip) are explicitly out of scope per the review brief and are NOT re-reported here.

## Warnings

### WR-01: Status bar overwrites bottom 12 px of minimap content

**File:** `open_perception.py:352-376` (`_draw_status_bar`), interacting with `openarena_perception/visualization/panels/minimap.py:65-68` (`_map_size` / `_map_top`)
**Issue:** The unified window is 760x720. `_draw_status_bar` paints a 20 px tall bar at `bar_y = PANEL_HEIGHT - 20 = 700` directly onto `self.screen`. Because `minimap_surf` is a subsurface sharing the same pixel buffer and spans absolute y=360..720, the status bar paints over the bottom 20 rows of the minimap subsurface (absolute y=700..720 → relative y=340..360 inside the minimap panel). MinimapPanel computes `_map_size = min(360 - 16, 360 - 24 - 8) = 328`, so the map square ends at relative y = `_map_top + _map_size = 24 + 328 = 352`. That means ~12 rows of actual map content (the southern strip of the drawn map, from relative y=340 to y=352) are overwritten every frame by the status bar fill. Items, route waypoints, or the player marker that happen to fall in the southernmost ~3.6% of the world bounds will be invisible. The stats panel is also clipped by the same 20 px strip, which the stats panel layout (verbose region y=470..700) appears to tolerate but was not re-verified for 12.1's new height.
**Fix:** Either reserve explicit vertical space for the status bar in the subsurface layout, or shrink the minimap drawable area so it does not collide. Two options:
```python
# Option A: shrink PANEL_HEIGHT to exclude status bar
# in panels/__init__.py
STATUS_BAR_H = 20
PANEL_HEIGHT = PANEL_WIREFRAME_SIZE + PANEL_MINIMAP_SIZE  # 720 panels
HUD_HEIGHT = PANEL_HEIGHT + STATUS_BAR_H                   # 740 total window
# and in OpenPerceptionApp:
self.screen = pygame.display.set_mode((HUD_WIDTH, HUD_HEIGHT))
# subsurfaces unchanged (still 0..720)
# status bar lives at y=720..740, OUTSIDE all panels
```
```python
# Option B: shrink minimap's drawable rect so its last drawn row is above 340
# in MinimapPanel.__init__:
bottom_reserved = 20  # status bar
self._map_size = min(
    width - 2 * self._map_margin,
    height - self._map_top - self._map_margin - bottom_reserved,
)
```
Option A is cleaner because it keeps the status bar out of panel space entirely, matching the docstring promise that each panel "never reach[es] outside the sub-surface they are handed."

### WR-02: `_draw_aas_overhead` silently swallows all exceptions

**File:** `openarena_perception/visualization/panels/minimap.py:76-79`
**Issue:** The new AAS overhead helper wraps `areas_on_floor` in a bare `except Exception: return`. Any bug introduced later in `areas_on_floor`, in attribute access on `self._aas_graph.areas`, or in `_world_to_minimap` coordinate math (e.g., a malformed synthetic graph) will be silently suppressed at 10 FPS with no logging. This is new code in 12.1, so the workaround is not pre-existing technical debt.
**Fix:** Narrow the catch and log once. Either catch only the expected failure mode (`AttributeError` / `IndexError` from malformed graphs) or log via the module logger:
```python
import logging
log = logging.getLogger(__name__)

def _draw_aas_overhead(self, state, surface):
    if self._aas_graph is None:
        return
    bot_z = float(getattr(state, "player_z", 0.0) or 0.0)
    try:
        floor_ids = areas_on_floor(self._aas_graph, bot_z, z_tolerance=24.0)
    except (AttributeError, IndexError, TypeError) as e:
        if not getattr(self, "_aas_overhead_warned", False):
            log.warning("AAS overhead disabled: %s", e)
            self._aas_overhead_warned = True
        return
    ...
```
The once-flag prevents log spam at the 10 FPS draw rate.

## Info

### IN-01: Hardcoded AAS overhead fill color instead of palette constant

**File:** `openarena_perception/visualization/panels/minimap.py:80`
**Issue:** `fill_color = (35, 45, 60)` is a magic tuple inline. Every other RGB color in the minimap comes from `panels/__init__.py` (`RGB_BG`, `RGB_GRID`, etc.), and Pitfall 2 in the package docstring explicitly says palette constants carry the `RGB_` prefix to prevent BGR/RGB mixing. The test `_count_aas_fill_pixels` hardcodes the same tuple (`tests/test_open_perception_panels.py:204`), duplicating the magic number.
**Fix:** Add to `panels/__init__.py`:
```python
RGB_AAS_FLOOR_FILL = (35, 45, 60)
```
then import and use it in minimap.py and the test. Keeps the palette single-sourced.

### IN-02: `_draw_separators` runs on top of waiting placeholder

**File:** `open_perception.py:391-403` (`draw_tick`)
**Issue:** When the state file is missing, `_draw_waiting_placeholder` fills the whole screen and draws a centered message. `draw_tick` then unconditionally calls `_draw_separators`, which paints vertical and horizontal separator lines across the placeholder. The effect is cosmetic (the placeholder still reads fine), but the separator lines bisect the centered "waiting for bot" message in a way that looks like a rendering glitch. The status bar behavior in waiting mode is correct.
**Fix:** Skip separators while waiting, or move the waiting text out of the separator crosshair region:
```python
def draw_tick(self) -> None:
    waiting = not self.state_file.exists()
    if waiting:
        self._draw_waiting_placeholder()
    else:
        self.screen.fill(RGB_BG)
        self.minimap.draw(self.state, self.minimap_surf)
        self.wireframe.draw(self.state, self.wireframe_surf)
        self.stats.draw(self.state, self.stats_surf)
        self._draw_separators()  # only when panels are live
    self._draw_status_bar(waiting)
    pygame.display.flip()
```

### IN-03: `_resolve_aas_path` auto-detect test pollutes repo `maps/` dir

**File:** `tests/test_open_perception.py:166-186` (`test_open_perception_aas_autodetect_from_state`)
**Issue:** The test monkeypatches `PROJECT_ROOT` to `tmp_path.parent`, then creates `tmp_path.parent / "maps" / "oa_dm1.aas"` with stub bytes, then unlinks just the file in `finally` — it leaves `tmp_path.parent / "maps"` directory behind. More importantly, if `tmp_path.parent` happens to be under the real repo on some environments, this would transiently overwrite `maps/oa_dm1.aas`. In practice `tmp_path.parent` is under `/tmp/pytest-of-*/`, so the risk is theoretical, but the pattern is fragile.
**Fix:** Point the override at a dedicated subdirectory of `tmp_path` instead:
```python
fake_root = tmp_path / "fake_project"
fake_maps = fake_root / "maps"
fake_maps.mkdir(parents=True)
target = fake_maps / "oa_dm1.aas"
target.write_bytes(b"stub")
monkeypatch.setattr(open_perception, "PROJECT_ROOT", fake_root)
resolved = open_perception._resolve_aas_path(None, "oa_dm1")
assert resolved == target
```
This keeps the test fully hermetic inside `tmp_path` and removes the `finally: unlink` dance.
